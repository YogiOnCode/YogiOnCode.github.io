Context

The problem

hello again is a loyalty platform. Shops already have a cash register, often from a vendor we have never worked with and sometimes decades old, and we may not change it.

The plugin runs next to it on the till. It reads each sale from whatever the POS gives off (a print job, a file, a barcode, a screen, a UI element), finds the loyalty customer, redeems rewards and sends the receipt to the backend.

The real screens are under NDA, so this page shows the design and the decisions instead.

Key decisions

The trade-offs that shaped it

Short architecture decision records: the situation, what I chose, and what it cost.

ADR-01Write every sale to disk before sending it

Context
Tills lose network for hours, and a receipt sent from memory is lost if the app restarts.
Decision
One atomic record per transaction with a state machine, retried by a background worker with exponential backoff, then a dead-letter state. Written as a decision record first: never replay a call whose result is already printed on the customer's paper receipt.
Trade-off
More disk I/O and more states to test; in exchange receipts survive offline periods and crashes without duplicates.

ADR-02Read print jobs through the spooler, not from its folder

Context
Copying spool files from disk races the spooler and can miss or truncate a receipt.
Decision
Read the job through the Win32 spooler API with bounded memory and a bounded wait, shipped behind a kill switch with the old path as fallback.
Trade-off
Two code paths to maintain during rollout, but a safe switch-over on live tills.

ADR-03Never redirect a child process's output without reading it

Context
Start-up and updates hung on loaded tills. The cause was a pipe deadlock around a child process.
Decision
No stream redirection, a hard timeout and a kill on expiry, applied everywhere the plugin starts a process.
Trade-off
Less output to log from those processes; no more hangs.

ADR-04Test before save, and move one till at a time

Context
Moving receipt processing in-house could break receipts for live merchants.
Decision
A config can only be saved after a dry run on real receipts with zero side effects. Each till's receipt endpoint comes from remote config, so merchants move one by one and can be switched back instantly.
Trade-off
A slower rollout than a big-bang switch, with no risky cut-over day.

ADR-05No agent framework next to production credentials

Context
Agent frameworks are quick to start with, but give the model a shell inside a container that holds production credentials.
Decision
A hand-written streaming tool loop on the Anthropic Messages API, with only read-only tools.
Trade-off
More code to own; in exchange a small, auditable surface with no channel out.

AI developments

A production AI agent, with guardrails

Finding out why a till stopped sending receipts used to take one person's laptop and memory. Now support asks a shared, audited agent from the dashboard. Every answer follows one report shape: verdict, timeline, code location, root cause, what was ruled out, how to verify.

RiskControl
Runaway cost
→
A dollar ceiling per requestPriced per token type and checked after every turn; plus a turn cap and bounded tool output.
Unauthorised use
→
Two gatesCloud Run IAM plus a constant-time shared secret; the identity token is verified to record which person asked.
Prompt injection
→
No channel outCallers cannot add system roles; logs are treated as untrusted data; no web, write or URL-fetch tools.
Leaking secrets
→
Removed at the sourceSecrets are stripped before the data reaches the agent, with redaction on every tool result as a backstop.
No accountability
→
Full audit trailA log line per request (question hashed, not stored) and an archive of every conversation, cancelled ones included.
